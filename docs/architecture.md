# GitZero architecture

## Product invariants

1. GitHub is the repository and pull-request UI, but no GitHub-hosted runner executes an onboarded repository's workflow.
2. Existing `.github/workflows` files are not rewritten for GitZero and do not need a `self-hosted` label.
3. The exact GitHub pull-request test merge SHA pinned during initialization defines the workflow graph and default checkout; checkout steps may explicitly select that merge snapshot or the authenticated webhook's exact head or base snapshot.
4. Runner credentials are short-lived, never written into a checkout, and never included in logs or observer events.
5. Every queued job is durable, every state transition is idempotent, and a disconnected or internally stalled agent's lease can be recovered.
6. Every GitHub Check GitZero creates reaches a terminal conclusion; a PR without a valid test merge snapshot terminates durably before Check creation.
7. Unsupported GitHub Actions behavior fails visibly. Compatibility is never inferred from a zero exit status after skipped work.

## Request and execution flow

```text
GitHub pull_request webhook
          |
          v
Cloudflare Worker -- HMAC + delivery validation
          |
          v
Workspace Durable Object (one per GitHub App installation)
  - durable job queue and leases
  - repository-scoped concurrency leases and wait queues
  - hibernatable agent/observer WebSockets
  - GitHub Check lifecycle
          |
          v
Rust agent on an available Mac Mini
  - authenticated checkout of the exact test merge SHA
  - workflow discovery and compatibility validation
  - concurrent dependency-ready jobs in empty isolated workspaces
  - bounded matrix and step/action process execution
  - batched logs and lifecycle events
          |
          v
Workspace Durable Object --> GitHub Check conclusion
```

The Durable Object is sharded by installation ID. This keeps coordination local to a workspace without turning the whole fleet into one global bottleneck. WebSocket attachments hold only reconnectable connection metadata; jobs and leases live in SQLite storage.

The webhook request performs bounded body reading, HMAC verification, payload validation, delivery deduplication, and durable job persistence before returning a 2xx response (`202` for a new job and `200` for the same delivery ID). It does not wait for GitHub API round trips. Exact merge-snapshot resolution, repository-variable capture, and initial Check creation run as leased job initialization after acknowledgement; an initializing job cannot be assigned to a Mac. When the signed event omits its merge SHA, GitZero uses a one-repository `pull_requests: read` token to read the PR, proves its current head and base still match the authenticated event, and pins the reported test merge commit. Pending mergeability uses the existing bounded exponential retry from Durable Object alarms, conflicts complete neutrally without execution, and changed head/base identity fails closed rather than running an unintended snapshot. Initialization retry state survives isolate restarts through SQLite state, appears in observer snapshots/events, and terminates visibly after eight attempts. On a retry, GitZero lists its Check Runs at the exact merge SHA and reuses only a `GitZero` run whose external ID equals the durable job ID, closing the crash window between GitHub accepting the Check and SQLite recording its ID. This keeps the delivery path inside GitHub's 10-second response contract without weakening the requirement that the immutable execution SHA, credentials, variables, and Check exist before execution begins.

Webhook admission covers every current GitHub `pull_request` activity type, including draft PRs. Workflow discovery applies GitHub's default activity set—`opened`, `synchronize`, and `reopened`—unless `types:` is present, in which case the declared activity is matched exactly. Because aggregate Check creation precedes agent-side discovery, an admitted activity with no matching workflow finishes the GitZero Check neutrally rather than creating no Check or reporting a successful build. Open and unmerged activity uses the immutable `refs/pull/<number>/merge` snapshot. For a merged `closed` event, the signed merge commit remains the execution SHA while the execution, workflow, cache, and default-checkout ref changes to `refs/heads/<base>`. That exact fully qualified execution ref wins over its base alias during explicit checkout, while other explicit head/base selectors remain pinned to the authenticated event snapshots.

An agent heartbeat renews only the job IDs that agent reports as running. Missing jobs retain their existing deadline and are recovered when the lease expires; an agent reporting a lease it no longer owns receives a cancellation message. Infrastructure failures are retried on another compatible Mac up to three assignments. Capability negotiation is separate from those retries: before starting, an agent may durably return the bounded, deterministically resolvable macOS/self-hosted runner requirements discovered at the exact PR merge SHA. The Durable Object releases that assignment without incrementing its effective attempt count, persists the requirements, marks that WebSocket as draining until a heartbeat confirms the local task disappeared, and scans the whole ready queue for the oldest job that any currently available Mac can satisfy. This prevents both local admission races and an incompatible head entry blocking unrelated compatible work. A run that exhausts real assignment attempts fails visibly, and work that cannot acquire a matching agent within 24 hours concludes as timed out. Each accepted delivery receives a monotonic workspace run number. The complete authenticated webhook event is stored in ordered chunks below Durable Object SQLite's per-row boundary, reconstructed only when a Mac is assigned, and omitted from observer snapshots. Completed jobs, event chunks, webhook deliveries, and protocol message IDs are retained for 30 days before opportunistic pruning.

An observer WebSocket receives an initial workspace snapshot followed by job lifecycle, capability rejection, log, agent online/offline, and `agent_status` heartbeat events. Snapshots retain each job's discovered runner requirements, while a rejection event names the Mac, bounded requirements, and non-secret reason. Each agent status includes connection and last-seen timestamps, canonical and custom runner labels, the optional runner group, active job leases, draining job IDs, maximum parallelism, and remaining capacity, so dashboards do not have to infer Mac health from log traffic.

Workflow- and job-level `concurrency` is coordinated in the same installation Durable Object but keyed by repository and a case-insensitive rendered group. The agent asks for a durable lease before the protected workflow, job, matrix cell, or reusable-workflow invocation starts and releases it only after the protected process tree or nested graph has stopped. The default `queue: single` retains one pending unit and cancels an older waiter when a newer unit arrives; `queue: max` retains up to 100 waiters and promotes them FIFO. Conditional `cancel-in-progress` moves the active lease into a cancelling state, signals its owning Mac over the existing WebSocket, and does not grant the replacement until that Mac releases the lease, preventing overlap during process shutdown. Reusable-call and called-workflow concurrency scopes are acquired at the invocation gate and held through its result gate, including nested and matrix calls. Lease rows survive isolate restarts, are removed on completion, requeue, or disconnect, and appear in observer snapshots and lifecycle events.

The macOS-only `npm run test:e2e` acceptance harness exercises that boundary without a Cloudflare account or GitHub repository. Local Wrangler runs the production Worker and SQLite Durable Object, two production Rust agent processes authenticate and complete their protocol handshakes, and an authenticated observer records the relayed stream. Two overlapping jobs target temporary exact pull-request head and merge refs and must be assigned to different agents, execute the real workflow from the merge snapshot, relay ordered queue/assignment/start/step/log/finish events, publish the shell-generated step summaries into terminal workspace snapshots, and return both agents to full capacity. A process-local Git URL rewrite maps the schema-valid fixture URL to the temporary bare repository only for those test agents; production URL validation and runtime code receive no test bypass. The harness uses generated secrets and isolated persistence, bounds startup and completion waits, terminates process groups, and deletes all temporary state on success or failure.

Each Mac admits at most its configured number of PR runs. Inside those runs, matching workflow files, dependency-ready base jobs, and eligible matrix instances may execute concurrently, but all runs share a second job-slot pool with the same configured limit. This prevents nested PR and workflow parallelism from multiplying host load. The executor renders string, list, expression, and `{group, labels}` `runs-on` selectors after the job condition, treats a lone GitHub-hosted `macos-*` label as compatible, and otherwise requires every label plus the optional group to match the selected agent case-insensitively. Agents always advertise `self-hosted`, `macOS`, and GitHub's native `ARM64` or `X64` spelling, with operator-defined labels and group added at installation. Before job start, the parsed expression AST identifies selectors and conditions that depend only on webhook-backed `github`, base `vars`, static `matrix`/`strategy`, and statically bound reusable-workflow `inputs`; those values are evaluated with the same runtime context construction, normalized, and deduplicated. Up to 512 distinct requirements, each with at most 32 bounded labels, may be negotiated back to the scheduler. Explicit GitHub-hosted Linux and Windows selectors bypass negotiation and reach the normal unsupported-runner failure instead of waiting for an impossible Mac. Expressions involving `needs`, dynamic matrices, status functions, workspace hashing, secrets, or runner/job/step/environment state stay runtime-only to avoid rejecting a Mac for a value that execution can still change. A matrix's `strategy.max-parallel` can impose a stricter local limit, and `strategy.fail-fast` cancels its running process trees and skips queued variants after a non-tolerated failure. Completed matrix outputs are merged in declared expansion order, and workflow failures are sorted before reporting, so scheduling order cannot change downstream results or summaries.

## Why GitZero is not a self-hosted runner label

GitHub routes jobs according to `jobs.<job_id>.runs-on`. A workflow using a GitHub-hosted label such as `macos-latest` cannot be redirected to a self-hosted machine through the supported runner registration APIs. Requiring `[self-hosted, macOS]` would violate the no-workflow-changes requirement.

GitZero therefore acts as a GitHub App CI provider: it listens for pull-request events, reads the repository's existing workflows, executes them independently, and writes Check Runs. Native Actions must be disabled for an onboarded repository through its settings/API so GitHub does not also schedule hosted runs.

Onboarding has an explicit two-step safety gate. The administrator-authenticated repository-readiness route combines the workspace snapshot with GitHub's repository Actions policy. A repository is safe to switch only when a protocol-compatible macOS agent is online and a locally successful job has a Check Run that GitHub independently reports as `GitZero`, `completed`, and `success` for the same external job ID and exact execution merge SHA. This read-only route uses one short-lived, single-repository token with `administration: read` and conditional `checks: read`.

The operator must then submit the exact job ID, Check Run ID, head SHA, and literal `disable_native_actions` confirmation to the administrator-authenticated onboarding route. It takes a fresh workspace snapshot, rejects stale local evidence before contacting GitHub, and repeats the repository policy and Check verification. Only then does it mint a separate short-lived, single-repository token with `administration: write`, set native Actions to disabled, and read the policy back before reporting completion. Repeating the confirmed request after completion performs no additional write. This route is never called by webhook processing, agent traffic, or retries.

## Compatibility boundary

Workflow and job concurrency supports literal or expression-rendered groups in GitHub's allowed contexts, including matrix cells and reusable-workflow inputs. Group identity is case-insensitive and repository-scoped. Both the default single-pending replacement mode and FIFO `queue: max` are supported, while `queue: max` with a true runtime `cancel-in-progress` fails visibly. A superseded active unit is reported as cancelled only after its process tree stops and its durable lease is released.

The current executor supports concurrent matching workflow files, pull-request activity and ordered base-branch/path filters, static and expression-driven matrix expansion (up to GitHub's 256-job limit), concurrent dependency scheduling, matrix `max-parallel` and fail-fast behavior, conditions and status functions, job and step outputs, run defaults, expression-driven job, workflow-step, and composite-step `continue-on-error`, command files, custom shell templates, JavaScript actions, composite actions with live `github.action_status`, inputs, action state, and post entrypoints. Job steps also support GitHub's `background: true`, single/list `wait`, `wait-all`, `cancel`, and `parallel` syntax. At most ten background steps own execution slots in one job while later entries remain queued. Each task evaluates against the context captured when it is scheduled; its outputs, environment changes, path additions, summaries, and registered action posts remain job-local until a matching wait or cancel flushes them in declared target order. Explicit cancellation sends the same process-tree termination path used by timeouts and is neutral unless the task had already failed. Every unconsumed task is implicitly drained and folded into the job result before LIFO post-action cleanup.

Every job starts with an empty isolated workspace and a unique fresh `RUNNER_TEMP`; workspace repository files appear only after the workflow runs `actions/checkout`. A `$/path` action instead materializes the repository containing the workflow at that workflow's exact commit into the separate action area, so it requires no checkout and does not populate the workspace. The same resolution is applied recursively: `$/` inside a composite binds to the repository and pinned commit containing that composite, while a `./` composite falls back to the containing workflow repository and SHA. Same-repository checkout defaults to the immutable pull-request merge snapshot and can explicitly materialize that merge, the webhook-authenticated head, or the exact base snapshot at the workspace root or a lexically contained relative `path`. It rejects symlink traversal, accepts only exact SHAs or safe aliases for those three snapshots, publishes the action's `ref` and `commit` outputs, supports repeated clean checkouts, and re-verifies `HEAD` after applying fetch, LFS, and submodule options. The default `set-safe-directory` input copies the inherited global Git configuration to a mode-0600 file in the job's temporary root, adds the canonical checkout path, and scopes that file to every Git process spawned by the checkout step, including local transports and submodule children. The temporary configuration is removed on every return path, `set-safe-directory: false` creates no override, and the Mac user's global configuration is never modified. A checkout token may be the built-in workflow token, explicitly empty for anonymous-only access, or an exact unmodified value from the managed-secret scope visible to that job. Submodule checkout synchronizes `.gitmodules`, forces its recorded commits, follows checkout depth and recursive selection, and disables automatic GC in each initialized repository. Without an SSH key, bounded inline Git configuration converts `git@github.com:` submodule URLs to HTTPS so they use the same selected token; unrelated workflow-supplied Git configuration remains intact. An exact managed-secret SSH private key instead selects GitHub's SSH transport for same- or cross-repository checkout. The bounded `ssh-user`, `ssh-known-hosts`, and `ssh-strict` inputs configure a trusted system SSH client without placing private-key material in its command line; the key and known-host data are mode-0600 job-temporary files, and only their paths persist to later steps when `persist-credentials` is true. Cross-repository checkout accepts a bounded GitHub `owner/repository` plus a bounded branch, tag, full commit, or default `HEAD` and first attempts anonymous access without sending the source repository's installation token. If that fails for a different target under the caller owner, the active Mac can obtain a separate App-installation token restricted to that target and `contents: read`. An explicit managed-secret token or SSH key bypasses anonymous and App-token fallback and can authorize a private cross-owner target; arbitrary literal or transformed credentials and private targets omitted from the installation when using App fallback fail closed. Checkout resolves and stores the commit once per PR run, reuses that resolution across jobs even if the remote ref moves, and verifies the exact commit after the same path, clean, depth, tag, sparse, filter, LFS, and submodule processing. Cone and non-cone sparse working trees use a blobless partial fetch by default; an explicit Git partial-clone `filter` takes transport precedence, and later checkout without sparse patterns disables the prior sparse configuration and restores the full tree. If a Git server cannot serve a filtered exact-SHA request, checkout falls back to the immutable per-run snapshot or retries the selected exact SHA without a filter; neither path re-resolves a moving ref. Independent jobs perform those checkouts concurrently. Integer step and job `timeout-minutes` values use GitHub's 360-minute maximum and default. An action step has one deadline covering acquisition and all JavaScript pre/main or nested composite work, so a phase transition cannot reset its timeout; expiry terminates the active process group and is still exposed as a failed step outcome when `continue-on-error` makes its conclusion successful. A job deadline is independent for every matrix cell and called-workflow job; expiry terminates the active process group, suppresses remaining steps and post entrypoints, propagates as a failed `needs` result, participates in fail-fast, and produces a distinct timed-out Check conclusion rather than being confused with external cancellation. Dynamic matrix objects or individual dimensions can be derived from prior `needs` job outputs with `fromJSON`; expansion happens only after those dependencies complete and the base job condition passes, matching GitHub's condition-before-matrix ordering. Public and owner-shared private remote actions are fetched from GitHub at their declared ref and materialized into isolated per-job directories. Node actions use the Node.js 24 runtime installed on the Mac.

Remote source repositories use a persistent bare object cache under the agent work root. A moving action, reusable-workflow, or checkout ref is fetched and resolved once per PR run, then pinned to that commit throughout the run; a later run refreshes the ref. Resolved commits are retained by internal cache refs. Actions receive lightweight per-job checkouts, while reusable workflow YAML is loaded before compilation from the pinned checkout. Public targets are fetched anonymously. If that acquisition fails for a target under the caller's GitHub owner, the agent asks the control plane for private shared-source access. The Durable Object proves that the requester still owns the active run; the Worker uses a target-only administration-read token to read GitHub's Actions access policy, accepts only the matching user/organization scope, and mints a different target-only contents-read token. Cross-owner targets, unavailable owner identity, missing App installation access, and disabled sharing fail closed. Target tokens are cached only for the run, added to global output masking before use, injected only into the Git process environment, cleared on completion, and never written to the object cache or workflow contexts. Shared-source, anonymous-checkout, managed-checkout, and SSH-checkout trees use separate namespaces even though their immutable Git objects and run-wide pinned ref share one cache. The cache keeps its canonical HTTPS origin even when an SSH purpose fetches through a selected SSH remote. Before an anonymous or SSH purpose consumes a resolution created elsewhere, it probes the selected remote with only that purpose's credentials; prior source authorization therefore cannot satisfy a checkout from cached files. Cache coordination is process-wide, so one agent process must exclusively own a work root.

Every run also receives a loopback-only Actions cache endpoint and an unguessable bearer token through the standard runner environment. The token joins the agent's global mask set before any workflow output is relayed. GitZero leaves the cache-v2 feature flag empty so current `@actions/cache` toolkit consumers—including `actions/cache@v5` and setup actions with integrated dependency caching—select their v1 REST client. The service implements exact and ordered prefix lookup, out-of-order ranged uploads, streamed downloads, immutable key/version commits, and the response shapes those unchanged clients expect. Entries are namespaced by case-insensitive repository identity and the exact `refs/pull/<number>/merge` scope, so one repository or pull request cannot restore another's data. Storage remains local to one Mac: agent reassignment can produce a safe cache miss, and cache contents are never treated as build inputs that must exist. By default each Mac admits entries up to 2 GiB within a 10 GiB total budget, expires entries after seven idle days, and evicts least-recently-used entries atomically before a commit. Operators can adjust those limits with `GITZERO_CACHE_MAX_ENTRY_BYTES` and `GITZERO_CACHE_MAX_BYTES`. A single agent process must continue to own its work root so the process-wide commit lock covers every concurrent run.

The same masked per-run token is JWT-shaped and carries the official `Actions.Results:<run-backend-id>:<job-backend-id>` scope. A second IPv4-loopback service exposes the current JSON Twirp artifact methods (`CreateArtifact`, `FinalizeArtifact`, `ListArtifacts`, `GetSignedArtifactURL`, and `DeleteArtifact`) plus the Azure Block Blob staging/commit/download behavior used by the official toolkit. This lets unchanged `actions/upload-artifact@v4+` and `actions/download-artifact@v4+` transfer zip archives or direct files between dependency-ordered jobs inside one assigned run. Names are immutable unless the official overwrite flow deletes them first; backend IDs and bearer credentials are checked on every control request, signed blob URLs reuse the already masked secret, upload bodies and block lists are streamed or bounded, and final size plus SHA-256 are verified before publication. The agent defaults to a 2 GiB per-artifact and 10 GiB per-run budget, configurable with `GITZERO_ARTIFACT_MAX_ENTRY_BYTES` and `GITZERO_ARTIFACT_MAX_BYTES`. Artifact state lives under the isolated run directory and is removed after completion. It is therefore unavailable after a retry on another Mac or after the run, is not registered in GitHub's artifact UI or public API, and cannot support `github-token` cross-run/cross-repository downloads. The upload action's `artifact-id` and digest outputs are valid within the run; its GitHub `artifact-url` output has no backing GitHub artifact record.

Reusable workflows are linked recursively up to ten total workflow levels and 50 unique called workflows. Same-repository `./` and `$/` references are read from the exact pull-request commit. Explicit `owner/repository/.github/workflows/file@ref` references are resolved once per PR run; the same-repository form uses the scoped checkout token, public targets remain anonymous, and private targets use the fail-closed same-owner Actions-sharing flow above. Nested relative calls inside a remote workflow remain pinned to that remote repository and ref. GitZero rejects call cycles, validates every `workflow_call`, preserves string/boolean/number input types and defaults at each nesting level, exposes only the immediate callee's `inputs` inside called jobs, maps called-workflow `jobs` and internal `needs`, publishes declared workflow outputs through every caller job, and carries the effective job-scoped built-in token through either `secrets: inherit` or named aliases whose values directly reference `github.token`, `secrets.GITHUB_TOKEN`, or an alias available to the immediate caller. Administrator-managed secrets use the same inheritance and named-reference rules. A target repository's source-download token never enters those contexts. Secret availability is recomputed at every direct call, so a nested workflow receives only the names its caller inherits or explicitly passes. Required aliases fail visibly when their source is unavailable, and literal secret values are rejected without being echoed. Caller `needs` and conditions retain their normal dependency behavior. Static and output-driven matrices on reusable-call jobs create an isolated called-workflow graph per matrix cell. For dynamic calls, the scheduler waits for `needs`, evaluates the call condition before the matrix expression, and inserts the expanded graphs into the running dependency DAG. It enforces `max-parallel`, cancels active and skips queued invocations on fail-fast, and selects outputs from successful invocations in completion order for both matrix forms. Private sources outside the caller's native sharing scope and literal reusable secret values fail visibly.

When at least one candidate workflow declares `paths` or `paths-ignore`, the Mac fetches the pull request's changed-file list through GitHub's repository API before compiling the workflows. It evaluates ordered positive/negative patterns and the all-files `paths-ignore` rule against GitHub's bounded list of up to 3,000 files. Workflows without path filters do not incur this API request.

The expression engine implements GitHub coercion, property/index/wildcard access, interpolation, status functions, the common string/JSON functions, and runner-side `hashFiles`. Missing object properties and out-of-range indexes follow GitHub's empty-string fallback behavior. At enqueue, the control plane snapshots all repository variables and organization variables GitHub reports as shared with that repository. Repository names take precedence case-insensitively; each scope is processed alphabetically under GitHub's combined 256 KiB per-run boundary. The resulting base `vars` context is stable across queue delay and agent reassignment and remains available inside called workflows from the caller repository. A runnable job may select an environment by literal or expression-driven name. After its job condition and runner label resolve, the Mac uses a separate internal token to retrieve that environment's metadata before any workspace or secret access. An unrestricted policy proceeds directly. Custom branch/tag policies are bounded and paginated, then matched case-sensitively with GitHub's path-aware `File.fnmatch` behavior: branch and tag refs use their names, while a pull-request merge ref is matched as `refs/pull/<number>/merge`. A protected-branches-only policy reads the selected `refs/heads/*` branch's current protection state; as GitHub documents, every ref is allowed when the repository has no protected branches. Reviewer, wait-timer, and custom protection rules still fail closed because their approval gates cannot safely be emulated. After authorization, the agent retrieves up to 100 paginated variables, caches them for the run, and applies the environment scope case-insensitively only to that job's runtime `vars`; this scope is outside the shared 256 KiB boundary. For an accepted environment, the agent sends start and terminal lifecycle intent around the job. The Durable Object persists that intent before external I/O, creates one GitHub Deployment against the exact execution merge SHA, and publishes `in_progress`, `success`, `failure`, or `error` statuses. Environment URL expressions can use completed step outputs and are included in a successful terminal status as well as the final PR Check. Retry leases and alarms recover ambiguous deployment or status writes by matching the GitZero job/unit payload and exact desired status, preventing duplicate records. Observer snapshots expose the durable desired/synced state and bounded retry diagnostics. Object-form `environment.deployment: false` suppresses Deployment creation without suppressing metadata/branch-policy validation or environment-scoped variables. The engine exposes the complete signed webhook as `github.event` and `GITHUB_EVENT_PATH`, plus the standard actor and numeric identity, API URLs, repository owner, synthetic GitZero run ID, durable run number, workflow file/ref/SHA, job ID, and per-step action identity through their matching `github.*` and `GITHUB_*` names. Static and output-driven matrix jobs also receive GitHub's zero-based `strategy.job-index`, total job count, effective maximum parallelism, and fail-fast value. Default `GITHUB_*` and `RUNNER_*` values cannot be replaced by workflow environment maps or `GITHUB_ENV`. To match GitHub's `pull_request` execution context, `github.sha`, `GITHUB_SHA`, workflow SHA values, and default checkout use the pinned test merge commit, while PR and workflow ref values use `refs/pull/<number>/merge`. The signed event still exposes the exact head and base commits, and explicit same-repository checkout aliases can select either snapshot. Named branch aliases create a local branch with an `origin` upstream pinned to that authenticated commit, while raw SHAs and `refs/pull/*` remain detached; the default base ref on a merged `closed` event is likewise attached. During job execution, the repository-scoped installation token is available through the equivalent `github.token` and `secrets.GITHUB_TOKEN` properties; pre-job condition and matrix evaluation receives `github.token: null` and no secrets context. Neither the separate environment-read token nor its value enters an expression or process environment. Token values and the workflow token's Basic-auth encoding are masked from all relayed logs and summaries. File hashing follows GitHub's per-file and aggregate SHA-256 construction, ordered positive/negative glob behavior, hidden-file matching, implicit directory descendants, and empty-string result for no matches. It is rooted to the isolated job workspace, skips symlink targets outside that boundary, and has the runner's 120-second deadline. Runtime matrix values remain typed JSON rather than being flattened to strings before validation and expansion.

Managed GitZero secrets use a separate administrator-controlled store because GitHub Apps cannot retrieve GitHub-hosted secret plaintext. The Durable Object encrypts each value with randomized AES-256-GCM and authenticated metadata bound to the workspace and normalized scope identity before SQLite persistence. Organization/repository ciphertext is copied into a per-job queue snapshot; environment ciphertext is selected only after the Mac validates the chosen environment and its deployment branch policy. Protocol v14 returns plaintext only to the active owning Mac for a durable same-repository, non-Dependabot PR, revalidates ownership after decryption, and never broadcasts the response to observers. Environment, repository, and organization precedence is applied before the Mac registers every nonempty value as a run-wide mask. Values then enter `secrets` expressions without automatic process-environment export, and nested reusable workflows receive only explicitly mapped or inherited names.

The `runner` context reports the configured Mac agent name, `macOS`, the native architecture, `self-hosted`, the shared tool cache, and the current job's isolated temp root. `runner.debug` remains absent by default, matching GitHub's context contract instead of publishing a synthetic `0` value; GitZero does not currently expose GitHub's rerun diagnostic mode.

Every shell, JavaScript action phase, and nested composite step receives an isolated `GITHUB_STEP_SUMMARY` file. GitZero captures GitHub-flavored Markdown when the step ends, ignores a file the step deleted, and treats invalid UTF-8 or content over GitHub's 1 MiB per-step limit as a visible summary-upload warning without changing the step conclusion. It groups up to 20 step summaries per job, orders job groups by completion time, masks credentials, and appends the result to the final PR Check. The combined payload is bounded below the Checks API's 65,535-character summary limit, with an explicit truncation marker when necessary.

The stdout/stderr command processor also converts unchanged `::error`, `::warning`, and `::notice` commands into GitHub Check annotations. It applies GitHub's `.github` and line-one defaults, decodes command properties and data, maps absolute paths under the isolated checkout back to repository-relative paths, omits columns from multi-line ranges, and keeps a human-readable masked log line. GitZero enforces the runner's ten-annotation per-severity per-step limit and the Checks API's 50-annotation request limit. The Mac sends only the bounded, credential-masked annotations with the terminal result; the Durable Object stores each annotation in its own SQLite row in the same input turn as completion. Before a retryable terminal Check update, the Worker reads the Check's existing annotations and performs ordered multiset reconciliation, preserving intentional duplicates while preventing an alarm retry after an ambiguous external success from appending duplicates.

Unchanged actions and scripts may also register job-scoped matcher files with `::add-matcher::path` and remove them by case-insensitive owner or config file with `::remove-matcher`. GitZero accepts both repository-relative files and the absolute action-cache paths emitted by setup actions, but canonicalizes each path and requires it to remain inside the isolated run directory. A matcher file is limited to 256 KiB, 32 definitions, ten patterns per definition, and 128 active owners per job. New definitions replace existing owners in config order. The Mac strips ANSI color escapes before applying bounded Rust regular expressions, supports single-line and looping multiline capture inheritance, resets partial matches between steps, and leaves the original diagnostic visible in the log. Only existing files under the job workspace become repository-relative annotation paths; unrootable issues use the generic `.github` location. Severity, line, column, code, and message captures become bounded Check fields, then pass through the same per-step count limits and terminal credential masking as direct commands. Rust's regex engine guarantees linear-time matching, so hostile output cannot trigger the native runner's backtracking timeout failure mode.

Environment command files cannot replace `GITHUB_*` or `RUNNER_*` defaults and reject `NODE_OPTIONS` case-insensitively, matching GitHub's command-file security boundary. Path command files prepend entries one at a time: the last written path receives highest precedence, and re-adding a path moves it to the front instead of accumulating duplicates.

The outbound relay interprets the security-sensitive stdout/stderr workflow commands `::add-mask::{value}`, `::stop-commands::{token}`, and the matching resume token. Command data uses the toolkit's percent decoding, a multiword mask registers both the complete value and its whitespace-separated components, and masks remain scoped to the originating job while the final combined Check applies every job's mask. Recognized control lines are not sent to observers. Command suspension ends on the matching token or at step completion, and commands split across bounded log chunks are reassembled before processing. A job may register at most 1,024 values totaling 1 MiB; exceeding that boundary fails the relay closed instead of forwarding potentially sensitive output. Shell and action stdout is processed synchronously before command files are read, so a `GITHUB_OUTPUT` entry containing either a configured credential or a dynamically masked value is skipped with a visible warning. GitZero retains the output name with an empty value so unchanged downstream expressions cannot recover the secret or fail on a missing property.

GitZero currently rejects container and service jobs, Docker actions, reusable-workflow secret values other than named references or `inherit`, GitHub environment reviewer/wait-timer/custom protection gates, OIDC workflow-token permissions, and `write-all` because it implicitly includes OIDC. Same-repository checkout accepts the built-in `github.token` explicitly or by default, an explicit empty token for anonymous access, or an exact value from the managed-secret scope visible to the job. Cross-repository checkout interprets a missing or built-in token as anonymous-first with managed same-owner App fallback, while an explicit empty token disables that fallback and an exact managed-secret value is used directly for the target. Either checkout mode also accepts an exact managed-secret `ssh-key`; optional `ssh-known-hosts`, `ssh-strict`, and `ssh-user` configure the system SSH transport, while literal or transformed keys are rejected. Private action/reusable-source, anonymous-checkout, managed-checkout, and SSH-checkout requests have distinct protocol purposes: only source acquisition consults GitHub's native Actions sharing policy, while App-fallback checkout requires the same owner and same App installation and receives a separately scoped contents-read token. Checkout supports depth/tag/LFS/submodule/clean/sparse/filter behavior and honors `set-safe-directory` without persisting its temporary global configuration beyond the action scope. Submodules are synchronized, forced to the commits recorded by the exact parent snapshot, use matching shallow depth and recursion, and receive GitHub SSH-to-HTTPS URL conversion only when no SSH key was selected. Sparse checkout requires Git 2.28 or newer. Persisted HTTPS Git credentials and submodule URL conversion live only in the job process environment; persisted SSH credentials reference mode-0600 files under the job's isolated temporary root, which is removed on success, failure, timeout, or cancellation. Retained or GitHub-hosted artifacts, artifact public/API access, cross-run and cross-repository artifact downloads, automatic import of GitHub-hosted secret values, protected-environment approvals, cluster-shared cache storage, and pre-dispatch routing for selectors that depend on runtime state remain unavailable. Because the complete PR run has affinity to one load-balanced Mac, every Mac eligible for a repository must expose the possible values of those runtime-only selectors; the executor reports a mismatch rather than silently running the job on an ineligible Mac. With no `permissions` declaration, the built-in workflow token keeps GitZero's `contents: read` and `pull-requests: read` baseline. A top-level declaration applies to every job, a job declaration replaces it with the explicitly named read/write scopes and sets omitted scopes to none, `read-all` selects every GitHub-readable workflow scope, and `{}` exposes no token. A reusable workflow receives the per-scope minimum of its own declaration and the caller's maximum. For non-baseline sets, the active Mac asks the Durable Object for a fresh token scoped to the selected repository and exact permissions; the agent caches it only for the run, masks it before use, and clears it at completion. Before issuing any writes, the Durable Object reconstructs the bounded signed webhook from durable chunks and proves that the PR head repository is the base repository and the author is not Dependabot. Otherwise every requested write is reduced to read, including when the GitHub repository is configured to send write tokens to forks. OIDC remains unavailable. Managed secret scopes are compatible only through GitZero's separate encrypted store and are never granted to fork, Dependabot, manual, or unverifiable runs. Multi-step jobs can refresh between top-level steps, but a single shell/action step and its registered action post lifecycle must still finish within the credential's remaining lifetime.

## Security boundaries

- GitHub webhook bodies are bounded and authenticated with `X-Hub-Signature-256` before parsing.
- `X-GitHub-Delivery` is the idempotency key.
- Agent and observer WebSockets use separate bearer credentials; invalid requests are rejected before reaching a Durable Object. Agent credentials are HMAC-scoped to exactly one workspace and agent ID, so a Mac cannot select another GitHub installation or impersonate a differently named agent with the same token.
- GitHub App installation tokens are minted only when needed and expire after one hour. The Worker validates GitHub's authoritative expiry and includes it in protocol v14 grants. The Mac rejects a grant inside a five-minute safety window, evicts cached credentials before that window, and reacquires source, environment, private-target, and workflow credentials at their use boundaries. Workflow credentials are rechecked at every top-level step boundary; a single step and its registered action post lifecycle must still finish within the credential's remaining lifetime.
- Public `/healthz` is dependency-free liveness; authenticated `/readyz` locally verifies that the configured GitHub App ID and PKCS#1/PKCS#8 key can sign an RS256 JWT and that the webhook, agent-signing, administrator, and managed-secret encryption secrets are sufficiently long and pairwise distinct. Neither endpoint calls GitHub.
- Workflow tokens are restricted to the selected pull-request repository. The no-declaration baseline is `contents: read` plus `pull requests: read`; explicit workflow/job declarations produce a separate exact read/write token while OIDC remains unavailable. A request is accepted only from the Mac that still owns the active run, and ownership is revalidated after GitHub returns the token. The Worker derives the fork and Dependabot downgrade from the authenticated durable webhook rather than the agent request. Cross-repository checkout deliberately omits the source token; a same-owner private target may receive a different App-installation token restricted to that repository and `contents: read`. A trusted job may instead use an exact administrator-managed secret value as its explicit target credential, including across owners; it is already globally masked, never becomes `github.token`, and must be passed through each reusable-workflow boundary. A private action or reusable-workflow target is separately authorized through its native Actions access policy with an internal target-scoped administration-read token; the agent receives only a distinct target-scoped contents-read token, which is masked and cannot enter workflow contexts or satisfy checkout authorization. Separate check-update tokens add `checks: write` and are never sent to an agent.
- Workflow annotations cross the WebSocket only after static and dynamic credential masking and strict path/range/count validation. Problem-matcher configuration reads are size-bounded and canonicalized inside the isolated run, and matched file paths must resolve under the repository workspace. Annotations are persisted before Check synchronization and reconciled against GitHub before retries, so the Durable Object never relies on in-memory annotation state or blindly repeats an append-only API mutation.
- Repository readiness uses a separate single-repository token with `administration: read` and conditional `checks: read`. Administrative write access is requested only after administrator authentication, exact evidence matching, explicit confirmation, and fresh readiness verification; the resulting single-repository token is used only to disable native Actions and verify the setting.
- Actions cache endpoints bind only to IPv4 loopback. Their random per-run bearer tokens are masked before job execution, and their on-disk namespaces are repository and pull-request scoped.
- Environment metadata tokens are separately restricted to the selected repository with `actions: read` and `environments: read`; they reach only the trusted Mac's internal API client and are never exposed to workflow expressions or processes.
- Deployment lifecycle events carry no credential. The Worker alone mints a single-repository `deployments: write` token after proving that the reporting Mac still owns an authorized GitHub-backed job; durable intent and exact-payload/status reconciliation make retries idempotent.
- Complete SHA-1 and SHA-256 object IDs are accepted across control-plane and agent trust boundaries. Every snapshot in one run must use one format, and source, checkout, and shared remote caches are initialized with that format before fetching.
- Shell and action execution happens in a per-job workspace, but that workspace is not a security sandbox. Only run trusted pull requests on a persistent host. Untrusted fork PRs require a disposable Mac/VM or a separately enforced sandbox boundary.
