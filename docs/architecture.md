# GitZero architecture

## Product invariants

1. GitHub is the repository and pull-request UI, but no GitHub-hosted runner executes an onboarded repository's workflow.
2. Existing `.github/workflows` files are not rewritten for GitZero and do not need a `self-hosted` label.
3. The exact pull-request head SHA delivered by the authenticated webhook defines the workflow graph; checkout steps may select only that head snapshot or the webhook's exact base snapshot.
4. Runner credentials are short-lived, never written into a checkout, and never included in logs or observer events.
5. Every queued job is durable, every state transition is idempotent, and a disconnected or internally stalled agent's lease can be recovered.
6. A GitHub Check always reaches a terminal conclusion for every accepted run.
7. Unsupported GitHub Actions behavior fails visibly. Compatibility is never inferred from a zero exit status after skipped work.

## Request and execution flow

```text
GitHub pull_request webhook
          |
          v
Cloudflare Worker -- HMAC + delivery validation
          |
          v
Workspace Durable Object (one per GitHub App installation)
  - durable job queue and leases
  - repository-scoped concurrency leases and wait queues
  - hibernatable agent/observer WebSockets
  - GitHub Check lifecycle
          |
          v
Rust agent on an available Mac Mini
  - authenticated checkout of the exact head SHA
  - workflow discovery and compatibility validation
  - concurrent dependency-ready jobs in empty isolated workspaces
  - bounded matrix and step/action process execution
  - batched logs and lifecycle events
          |
          v
Workspace Durable Object --> GitHub Check conclusion
```

The Durable Object is sharded by installation ID. This keeps coordination local to a workspace without turning the whole fleet into one global bottleneck. WebSocket attachments hold only reconnectable connection metadata; jobs and leases live in SQLite storage.

The webhook request performs bounded body reading, HMAC verification, payload validation, delivery deduplication, and durable job persistence before returning a 2xx response (`202` for a new job and `200` for the same delivery ID). It does not wait for GitHub API round trips. Repository-variable capture and initial Check creation run as leased job initialization after acknowledgement; an initializing job cannot be assigned to a Mac. Initialization failures use bounded exponential retry from Durable Object alarms, survive isolate restarts through SQLite state, appear in observer snapshots/events, and terminate visibly after eight attempts. On a retry, GitZero first lists its Check Runs at the exact head SHA and reuses only a `GitZero` run whose external ID equals the durable job ID, closing the crash window between GitHub accepting the Check and SQLite recording its ID. This keeps the delivery path inside GitHub's 10-second response contract without weakening the requirement that credentials, variables, and the Check exist before execution begins.

An agent heartbeat renews only the job IDs that agent reports as running. Missing jobs retain their existing deadline and are recovered when the lease expires; an agent reporting a lease it no longer owns receives a cancellation message. Infrastructure failures are retried on another compatible Mac up to three assignments. Capability negotiation is separate from those retries: before starting, an agent may durably return the bounded, deterministically resolvable macOS/self-hosted runner requirements discovered at the exact PR SHA. The Durable Object releases that assignment without incrementing its effective attempt count, persists the requirements, marks that WebSocket as draining until a heartbeat confirms the local task disappeared, and scans the whole ready queue for the oldest job that any currently available Mac can satisfy. This prevents both local admission races and an incompatible head entry blocking unrelated compatible work. A run that exhausts real assignment attempts fails visibly, and work that cannot acquire a matching agent within 24 hours concludes as timed out. Each accepted delivery receives a monotonic workspace run number. The complete authenticated webhook event is stored in ordered chunks below Durable Object SQLite's per-row boundary, reconstructed only when a Mac is assigned, and omitted from observer snapshots. Completed jobs, event chunks, webhook deliveries, and protocol message IDs are retained for 30 days before opportunistic pruning.

An observer WebSocket receives an initial workspace snapshot followed by job lifecycle, capability rejection, log, agent online/offline, and `agent_status` heartbeat events. Snapshots retain each job's discovered runner requirements, while a rejection event names the Mac, bounded requirements, and non-secret reason. Each agent status includes connection and last-seen timestamps, canonical and custom runner labels, the optional runner group, active job leases, draining job IDs, maximum parallelism, and remaining capacity, so dashboards do not have to infer Mac health from log traffic.

Workflow- and job-level `concurrency` is coordinated in the same installation Durable Object but keyed by repository and a case-insensitive rendered group. The agent asks for a durable lease before the protected workflow, job, matrix cell, or reusable-workflow invocation starts and releases it only after the protected process tree or nested graph has stopped. The default `queue: single` retains one pending unit and cancels an older waiter when a newer unit arrives; `queue: max` retains up to 100 waiters and promotes them FIFO. Conditional `cancel-in-progress` moves the active lease into a cancelling state, signals its owning Mac over the existing WebSocket, and does not grant the replacement until that Mac releases the lease, preventing overlap during process shutdown. Reusable-call and called-workflow concurrency scopes are acquired at the invocation gate and held through its result gate, including nested and matrix calls. Lease rows survive isolate restarts, are removed on completion, requeue, or disconnect, and appear in observer snapshots and lifecycle events.

The macOS-only `npm run test:e2e` acceptance harness exercises that boundary without a Cloudflare account or GitHub repository. Local Wrangler runs the production Worker and SQLite Durable Object, two production Rust agent processes authenticate and complete their protocol handshakes, and an authenticated observer records the relayed stream. Two overlapping jobs target a temporary exact pull-request ref and must be assigned to different agents, execute its real workflow, relay ordered queue/assignment/start/step/log/finish events, publish the shell-generated step summaries into terminal workspace snapshots, and return both agents to full capacity. A process-local Git URL rewrite maps the schema-valid fixture URL to the temporary bare repository only for those test agents; production URL validation and runtime code receive no test bypass. The harness uses generated secrets and isolated persistence, bounds startup and completion waits, terminates process groups, and deletes all temporary state on success or failure.

Each Mac admits at most its configured number of PR runs. Inside those runs, matching workflow files, dependency-ready base jobs, and eligible matrix instances may execute concurrently, but all runs share a second job-slot pool with the same configured limit. This prevents nested PR and workflow parallelism from multiplying host load. The executor renders string, list, expression, and `{group, labels}` `runs-on` selectors after the job condition, treats a lone GitHub-hosted `macos-*` label as compatible, and otherwise requires every label plus the optional group to match the selected agent case-insensitively. Agents always advertise `self-hosted`, `macOS`, and GitHub's native `ARM64` or `X64` spelling, with operator-defined labels and group added at installation. Before job start, the parsed expression AST identifies selectors and conditions that depend only on webhook-backed `github`, base `vars`, static `matrix`/`strategy`, and statically bound reusable-workflow `inputs`; those values are evaluated with the same runtime context construction, normalized, and deduplicated. Up to 512 distinct requirements, each with at most 32 bounded labels, may be negotiated back to the scheduler. Explicit GitHub-hosted Linux and Windows selectors bypass negotiation and reach the normal unsupported-runner failure instead of waiting for an impossible Mac. Expressions involving `needs`, dynamic matrices, status functions, workspace hashing, secrets, or runner/job/step/environment state stay runtime-only to avoid rejecting a Mac for a value that execution can still change. A matrix's `strategy.max-parallel` can impose a stricter local limit, and `strategy.fail-fast` cancels its running process trees and skips queued variants after a non-tolerated failure. Completed matrix outputs are merged in declared expansion order, and workflow failures are sorted before reporting, so scheduling order cannot change downstream results or summaries.

## Why GitZero is not a self-hosted runner label

GitHub routes jobs according to `jobs.<job_id>.runs-on`. A workflow using a GitHub-hosted label such as `macos-latest` cannot be redirected to a self-hosted machine through the supported runner registration APIs. Requiring `[self-hosted, macOS]` would violate the no-workflow-changes requirement.

GitZero therefore acts as a GitHub App CI provider: it listens for pull-request events, reads the repository's existing workflows, executes them independently, and writes Check Runs. Native Actions must be disabled for an onboarded repository through its settings/API so GitHub does not also schedule hosted runs.

Onboarding has an explicit two-step safety gate. The administrator-authenticated repository-readiness route combines the workspace snapshot with GitHub's repository Actions policy. A repository is safe to switch only when a protocol-compatible macOS agent is online and a locally successful job has a Check Run that GitHub independently reports as `GitZero`, `completed`, and `success` for the same external job ID and exact head SHA. This read-only route uses one short-lived, single-repository token with `administration: read` and conditional `checks: read`.

The operator must then submit the exact job ID, Check Run ID, head SHA, and literal `disable_native_actions` confirmation to the administrator-authenticated onboarding route. It takes a fresh workspace snapshot, rejects stale local evidence before contacting GitHub, and repeats the repository policy and Check verification. Only then does it mint a separate short-lived, single-repository token with `administration: write`, set native Actions to disabled, and read the policy back before reporting completion. Repeating the confirmed request after completion performs no additional write. This route is never called by webhook processing, agent traffic, or retries.

## Compatibility boundary

Workflow and job concurrency supports literal or expression-rendered groups in GitHub's allowed contexts, including matrix cells and reusable-workflow inputs. Group identity is case-insensitive and repository-scoped. Both the default single-pending replacement mode and FIFO `queue: max` are supported, while `queue: max` with a true runtime `cancel-in-progress` fails visibly. A superseded active unit is reported as cancelled only after its process tree stops and its durable lease is released.

The current executor supports concurrent matching workflow files, pull-request activity and ordered base-branch/path filters, static and expression-driven matrix expansion (up to GitHub's 256-job limit), concurrent dependency scheduling, matrix `max-parallel` and fail-fast behavior, conditions and status functions, job and step outputs, run defaults, expression-driven job, workflow-step, and composite-step `continue-on-error`, command files, custom shell templates, JavaScript actions, composite actions with live `github.action_status`, inputs, action state, and post entrypoints. Every job starts with an empty isolated workspace and a unique fresh `RUNNER_TEMP`; repository files appear only after the workflow runs `actions/checkout`. Same-repository checkout materializes either webhook-authenticated PR head or base snapshot at the workspace root or a lexically contained relative `path`, rejects symlink traversal, accepts only either exact SHA or aliases that map to those snapshots, publishes the action's `ref` and `commit` outputs, supports repeated clean checkouts, and re-verifies `HEAD` after applying fetch, LFS, and submodule options. Public cross-repository checkout accepts a bounded GitHub `owner/repository` plus a bounded branch, tag, full commit, or default `HEAD`, never sends the source repository's installation token, and therefore succeeds only when the target is publicly readable. It resolves and stores the commit once per PR run, reuses that resolution across jobs even if the remote ref moves, and verifies the exact commit after the same path, clean, depth, tag, sparse, filter, LFS, and submodule processing. Cone and non-cone sparse working trees use a blobless partial fetch by default; an explicit Git partial-clone `filter` takes transport precedence, and later checkout without sparse patterns disables the prior sparse configuration and restores the full tree. If a Git server cannot serve a filtered exact-SHA request, checkout falls back to the immutable per-run snapshot or retries the selected exact SHA without a filter; neither path re-resolves a moving ref. Independent jobs perform those checkouts concurrently. Integer step and job `timeout-minutes` values use GitHub's 360-minute maximum and default. An action step has one deadline covering acquisition and all JavaScript pre/main or nested composite work, so a phase transition cannot reset its timeout; expiry terminates the active process group and is still exposed as a failed step outcome when `continue-on-error` makes its conclusion successful. A job deadline is independent for every matrix cell and called-workflow job; expiry terminates the active process group, suppresses remaining steps and post entrypoints, propagates as a failed `needs` result, participates in fail-fast, and produces a distinct timed-out Check conclusion rather than being confused with external cancellation. Dynamic matrix objects or individual dimensions can be derived from prior `needs` job outputs with `fromJSON`; expansion happens only after those dependencies complete and the base job condition passes, matching GitHub's condition-before-matrix ordering. Public remote actions are fetched from GitHub at their declared ref and materialized into isolated per-job directories. Private actions outside the pull-request repository are not yet supported. Node actions use the Node.js 24 runtime installed on the Mac.

Remote source repositories use a persistent bare object cache under the agent work root. A moving action or reusable-workflow ref is fetched and resolved once per PR run, then pinned to that commit throughout the run; a later run refreshes the ref. Resolved commits are retained by internal cache refs. Actions receive lightweight per-job checkouts, while reusable workflow YAML is loaded before compilation from the pinned checkout. Fetch credentials are injected only into the Git process environment and are never written to the cache. Cache coordination is process-wide, so one agent process must exclusively own a work root.

Every run also receives a loopback-only Actions cache endpoint and an unguessable bearer token through the standard runner environment. The token joins the agent's global mask set before any workflow output is relayed. GitZero leaves the cache-v2 feature flag empty so current `@actions/cache` toolkit consumers—including `actions/cache@v5` and setup actions with integrated dependency caching—select their v1 REST client. The service implements exact and ordered prefix lookup, out-of-order ranged uploads, streamed downloads, immutable key/version commits, and the response shapes those unchanged clients expect. Entries are namespaced by case-insensitive repository identity and the exact `refs/pull/<number>/head` scope, so one repository or pull request cannot restore another's data. Storage remains local to one Mac: agent reassignment can produce a safe cache miss, and cache contents are never treated as build inputs that must exist. By default each Mac admits entries up to 2 GiB within a 10 GiB total budget, expires entries after seven idle days, and evicts least-recently-used entries atomically before a commit. Operators can adjust those limits with `GITZERO_CACHE_MAX_ENTRY_BYTES` and `GITZERO_CACHE_MAX_BYTES`. A single agent process must continue to own its work root so the process-wide commit lock covers every concurrent run.

The same masked per-run token is JWT-shaped and carries the official `Actions.Results:<run-backend-id>:<job-backend-id>` scope. A second IPv4-loopback service exposes the current JSON Twirp artifact methods (`CreateArtifact`, `FinalizeArtifact`, `ListArtifacts`, `GetSignedArtifactURL`, and `DeleteArtifact`) plus the Azure Block Blob staging/commit/download behavior used by the official toolkit. This lets unchanged `actions/upload-artifact@v4+` and `actions/download-artifact@v4+` transfer zip archives or direct files between dependency-ordered jobs inside one assigned run. Names are immutable unless the official overwrite flow deletes them first; backend IDs and bearer credentials are checked on every control request, signed blob URLs reuse the already masked secret, upload bodies and block lists are streamed or bounded, and final size plus SHA-256 are verified before publication. The agent defaults to a 2 GiB per-artifact and 10 GiB per-run budget, configurable with `GITZERO_ARTIFACT_MAX_ENTRY_BYTES` and `GITZERO_ARTIFACT_MAX_BYTES`. Artifact state lives under the isolated run directory and is removed after completion. It is therefore unavailable after a retry on another Mac or after the run, is not registered in GitHub's artifact UI or public API, and cannot support `github-token` cross-run/cross-repository downloads. The upload action's `artifact-id` and digest outputs are valid within the run; its GitHub `artifact-url` output has no backing GitHub artifact record.

Reusable workflows are linked recursively up to ten total workflow levels and 50 unique called workflows. Same-repository `./` and `$/` references are read from the exact pull-request commit. Explicit `owner/repository/.github/workflows/file@ref` references are resolved once per PR run; the same-repository form may use the scoped checkout token, while cross-repository acquisition is limited to public repositories so runner credentials are never broadened. Nested relative calls inside a remote workflow remain pinned to that remote repository and ref. GitZero rejects call cycles, validates every `workflow_call`, preserves string/boolean/number input types and defaults at each nesting level, exposes only the immediate callee's `inputs` inside called jobs, maps called-workflow `jobs` and internal `needs`, publishes declared workflow outputs through every caller job, and carries the fixed built-in token through either `secrets: inherit` or named aliases whose values directly reference `github.token`, `secrets.GITHUB_TOKEN`, or an alias available to the immediate caller. Secret availability is recomputed at every direct call, so a nested workflow receives only the names its caller inherits or explicitly passes. Required aliases fail visibly when their source is unavailable, and literal secret values are rejected without being echoed. Caller `needs` and conditions retain their normal dependency behavior. Static and output-driven matrices on reusable-call jobs create an isolated called-workflow graph per matrix cell. For dynamic calls, the scheduler waits for `needs`, evaluates the call condition before the matrix expression, and inserts the expanded graphs into the running dependency DAG. It enforces `max-parallel`, cancels active and skips queued invocations on fail-fast, and selects outputs from successful invocations in completion order for both matrix forms. Private cross-repository calls and custom reusable secrets that are not aliases of the built-in token fail visibly.

When at least one candidate workflow declares `paths` or `paths-ignore`, the Mac fetches the pull request's changed-file list through GitHub's repository API before compiling the workflows. It evaluates ordered positive/negative patterns and the all-files `paths-ignore` rule against GitHub's bounded list of up to 3,000 files. Workflows without path filters do not incur this API request.

The expression engine implements GitHub coercion, property/index/wildcard access, interpolation, status functions, the common string/JSON functions, and runner-side `hashFiles`. Missing object properties and out-of-range indexes follow GitHub's empty-string fallback behavior. At enqueue, the control plane snapshots all repository variables and organization variables GitHub reports as shared with that repository. Repository names take precedence case-insensitively; each scope is processed alphabetically under GitHub's combined 256 KiB per-run boundary. The resulting base `vars` context is stable across queue delay and agent reassignment and remains available inside called workflows from the caller repository. A runnable job may select an environment by literal or expression-driven name. After its job condition and runner label resolve, the Mac uses a separate internal token to retrieve that environment's metadata and paginated variables, caches the result for the run, and applies the environment scope case-insensitively only to that job's runtime `vars`. The 100-variable environment scope is outside the shared 256 KiB boundary. Environment URL expressions can use completed step outputs and are surfaced in the final PR Check. Environments with protection or branch rules fail before workspace preparation because reviewer/wait/custom gates cannot safely be emulated. The engine exposes the complete signed webhook as `github.event` and `GITHUB_EVENT_PATH`, plus the standard actor and numeric identity, API URLs, repository owner, synthetic GitZero run ID, durable run number, workflow file/ref/SHA, job ID, and per-step action identity through their matching `github.*` and `GITHUB_*` names. Static and output-driven matrix jobs also receive GitHub's zero-based `strategy.job-index`, total job count, effective maximum parallelism, and fail-fast value. Default `GITHUB_*` and `RUNNER_*` values cannot be replaced by workflow environment maps or `GITHUB_ENV`. Because GitZero deliberately executes the exact PR head rather than GitHub's synthetic merge commit, its PR ref values use `refs/pull/<number>/head`; the workflow ref follows the same exact-head contract. During job execution, the repository-scoped installation token is available through the equivalent `github.token` and `secrets.GITHUB_TOKEN` properties; pre-job condition and matrix evaluation receives `github.token: null` and no secrets context. Neither the separate environment-read token nor its value enters an expression or process environment. Token values and the workflow token's Basic-auth encoding are masked from all relayed logs and summaries. File hashing follows GitHub's per-file and aggregate SHA-256 construction, ordered positive/negative glob behavior, hidden-file matching, implicit directory descendants, and empty-string result for no matches. It is rooted to the isolated job workspace, skips symlink targets outside that boundary, and has the runner's 120-second deadline. Runtime matrix values remain typed JSON rather than being flattened to strings before validation and expansion.

The `runner` context reports the configured Mac agent name, `macOS`, the native architecture, `self-hosted`, the shared tool cache, and the current job's isolated temp root. `runner.debug` remains absent by default, matching GitHub's context contract instead of publishing a synthetic `0` value; GitZero does not currently expose GitHub's rerun diagnostic mode.

Every shell, JavaScript action phase, and nested composite step receives an isolated `GITHUB_STEP_SUMMARY` file. GitZero captures GitHub-flavored Markdown when the step ends, ignores a file the step deleted, and treats invalid UTF-8 or content over GitHub's 1 MiB per-step limit as a visible summary-upload warning without changing the step conclusion. It groups up to 20 step summaries per job, orders job groups by completion time, masks credentials, and appends the result to the final PR Check. The combined payload is bounded below the Checks API's 65,535-character summary limit, with an explicit truncation marker when necessary.

Environment command files cannot replace `GITHUB_*` or `RUNNER_*` defaults and reject `NODE_OPTIONS` case-insensitively, matching GitHub's command-file security boundary. Path command files prepend entries one at a time: the last written path receives highest precedence, and re-adding a path moves it to the front instead of accumulating duplicates.

The outbound relay interprets the security-sensitive stdout/stderr workflow commands `::add-mask::{value}`, `::stop-commands::{token}`, and the matching resume token. Command data uses the toolkit's percent decoding, a multiword mask registers both the complete value and its whitespace-separated components, and masks remain scoped to the originating job while the final combined Check applies every job's mask. Recognized control lines are not sent to observers. Command suspension ends on the matching token or at step completion, and commands split across bounded log chunks are reassembled before processing. A job may register at most 1,024 values totaling 1 MiB; exceeding that boundary fails the relay closed instead of forwarding potentially sensitive output. Shell and action stdout is processed synchronously before command files are read, so a `GITHUB_OUTPUT` entry containing either a configured credential or a dynamically masked value is skipped with a visible warning. GitZero retains the output name with an empty value so unchanged downstream expressions cannot recover the secret or fail on a missing property.

GitZero currently rejects container and service jobs, Docker actions, private cross-repository reusable workflows, reusable-workflow secret sources other than the built-in token and its directly passed aliases, protected GitHub environments, private cross-repository checkout, and custom checkout credentials. Same-repository checkout accepts the built-in `github.token` explicitly or by default and permits an explicit empty token for anonymous access; public cross-repository checkout uses anonymous access even when the unchanged action input resolves to the built-in token. Both support depth/tag/LFS/submodule/clean/sparse/filter behavior. Sparse checkout requires Git 2.28 or newer. Persisted Git credentials live only in the job process environment. Retained or GitHub-hosted artifacts, artifact public/API access, cross-run and cross-repository artifact downloads, custom Actions secrets, environment secrets, protected-environment approvals, Deployment records, cluster-shared cache storage, and pre-dispatch routing for selectors that depend on runtime state remain unavailable. Because the complete PR run has affinity to one load-balanced Mac, every Mac eligible for a repository must expose the possible values of those runtime-only selectors; the executor reports a mismatch rather than silently running the job on an ineligible Mac. The built-in workflow token always has the control plane's fixed `contents: read` and `pull_requests: read` permissions for exactly the selected repository and expires after one hour; parsed `permissions` blocks cannot broaden that token. Workflows that need write access, other permission families, custom secrets, or jobs longer than the token lifetime are not yet compatible.

## Security boundaries

- GitHub webhook bodies are bounded and authenticated with `X-Hub-Signature-256` before parsing.
- `X-GitHub-Delivery` is the idempotency key.
- Agent and observer WebSockets use separate bearer credentials; invalid requests are rejected before reaching a Durable Object. Agent credentials are HMAC-scoped to exactly one workspace and agent ID, so a Mac cannot select another GitHub installation or impersonate a differently named agent with the same token.
- GitHub App installation tokens are minted only when needed and expire after one hour.
- Public `/healthz` is dependency-free liveness; authenticated `/readyz` locally verifies that the configured GitHub App ID and PKCS#1/PKCS#8 key can sign an RS256 JWT and that the three control-plane secrets are sufficiently long and distinct. Neither endpoint calls GitHub.
- Workflow/checkout tokens are restricted to the selected pull-request repository with `contents: read` and `pull requests: read`; public cross-repository checkout deliberately omits that token, while private/custom-credential checkout is rejected. Separate check-update tokens add `checks: write` and are never sent to an agent.
- Repository readiness uses a separate single-repository token with `administration: read` and conditional `checks: read`. Administrative write access is requested only after administrator authentication, exact evidence matching, explicit confirmation, and fresh readiness verification; the resulting single-repository token is used only to disable native Actions and verify the setting.
- Actions cache endpoints bind only to IPv4 loopback. Their random per-run bearer tokens are masked before job execution, and their on-disk namespaces are repository and pull-request scoped.
- Environment metadata tokens are separately restricted to the selected repository with `actions: read` and `environments: read`; they reach only the trusted Mac's internal API client and are never exposed to workflow expressions or processes.
- Shell and action execution happens in a per-job workspace, but that workspace is not a security sandbox. Only run trusted pull requests on a persistent host. Untrusted fork PRs require a disposable Mac/VM or a separately enforced sandbox boundary.
